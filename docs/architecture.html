cr8 technical overview

One private music archive, rebuilt as a living instrument

How unreleased music becomes a fast shared catalog, a private streaming app, a tagging surface, a stem machine, and a deployable service — without moving the archive into somebody else’s cloud.

The read

cr8 turns a private, messy, unreleased music archive into a live social instrument without uploading that archive into a platform. The catalog can live on a machine you control. The app can be reachable anywhere. Friends can listen, tag, send, upload, and separate stems. The original files remain read-only.

The thesis is not “one computer can serve music.” The thesis is that unreleased creative work needs a different product shape from released music. Streaming apps, file shares, sample marketplaces, and folder trees all fail in different ways because they treat the file, the finished song, the share link, or the library as the center. cr8 makes the act of listening and deciding the center.

What existed at the beginning

The starting point was not a product spec. It was a hard drive full of music: demos, jams, half-finished ideas, multiple versions of the same track. Filenames carried dates, titles, keys, and version numbers often enough to parse. Project folders mattered. “Eras” were periods of making, not genres.

The problem was retrieval. A good bounce could exist, but nobody could find it when it mattered. Sending a track meant remembering a filename, hunting a folder, uploading a file, and hoping the reply arrived with enough context to mean anything. The work was technically stored and practically missing.

The first architecture: never touch the corpus

The first durable decision was negative: cr8 does not write into the music archive. It scans the corpus, parses what it can, and writes opinions into a database. The corpus is authority. The catalog is interpretation. The mirror is disposable. That split is why the system can move quickly without risking years of unreleased work.

The Python package owns the pipeline. cr8 scan walks configured roots and classifies files. Resolve groups bounces into songs. Enrichment imports key, BPM, fingerprints, and human corrections. Build creates streamable audio, waveform peaks, covers, and later stem mirrors. Verify proves that catalog, mirror, and claims still agree.

The app’s important data model is not a single track table. It is relationships: songs, bounces, users, sessions, reactions, listen progress, collections, shares, invites, uploads, assignments, jobs, stems. That is how listening grows into homework, presence, and public links without changing the core.

The route a tap actually takes

When someone presses play far from the machine that holds the archive, the expensive part of “feeling fast” should not all travel to that machine. The app shell, JavaScript, CSS, and warm static routes can live near the listener. The origin answers the parts that must come from the private catalog and media mirror: API truth, range audio, art.

In production shape, a public HTTPS face fronts a Next.js app that same-origin proxies to a local FastAPI owner process. Missing rewrites are scar tissue: if the browser can’t reach an API path through the web origin, features die quietly. The proxy list is load-bearing.

Architecture diagram

A request is best read in zones: listener, edge, web shell, API/catalog, derived media. The first zones are about feeling instant. The last two are about not lying and not mutating the archive.

Why it feels fast

Audio is range-served. The library is virtualized. Payload budgets, interaction budgets, and play-latency budgets are enforced in a gate that can refuse a deploy. Speed is not a vibe; it is a ship condition.

Latency-sensitive work should be near the listener when possible. Durable work — catalog truth, secrets, the corpus path — stays home.

The interface became a listening instrument

The UI is organized around continuous listening: a dock, a library that digs, filters that don’t fight you, tags that write while music plays, shares that open as honest pages. Empty states render nothing ornamental. Color comes from data (Camelot keys, eras), not from a theme pack.

What each subsystem is for

  • Pipeline (cr8) — scan, resolve, enrich, build, verify
  • Catalog (SQLite) — songs, people, reactions, shares, jobs
  • Owner API (FastAPI) — authenticated app surface and public share landings
  • Web (Next.js) — the listening instrument
  • Ops — deploy, tunnels, launch agents (identity via env, not hardcoded hosts)

The constraints made the shape

Never write the corpus. Prefer rebuildable mirrors. Keep secrets and operator identity out of the public tree. Measure what a visitor pays (JS bytes, play latency) and refuse to ship when the numbers lie.

What should stay open

The software is MIT. Anyone can run a crate. Circles form with invites and shares. Federation can come later; clean boundaries now make that future possible without forcing a platform.
