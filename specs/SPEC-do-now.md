# DO-NOW: the ten that fix the loop (from 5-loop synthesis, verified against catalog.db)

Verified 2026-07-30: song_tags=55 (33 collab/filename + 22 instr/proposed, ZERO human vibe),
reactions=13, eras table=0 rows, 376/472 songs single-version, 75 songs undated,
status: 471 demo + 1 released. The archive is effectively untagged — design empty-first.

## 1. Transport reflects state; the playing row is visibly marked
**Why:** QA #1 calls it "the single worst bug" and it is still unfixed in the working tree: playback.js binds only `timeupdate` (:568) and `ended` (:581) — there are no play/pause/waiting/error listeners at all. The glyph is a static triangle and the aria-label is the permanently ambiguous "Play or pause". Nothing anywhere marks which of 472 rows is playing. Already ruled on by SPEC-v2 §6.1 and given exact values by SPEC-craft §8 — this is implementation, not design.
**How:** In `cr8/web/common/static/playback.js`, bind `play`, `pause`, `waiting`, `playing`, `error` and set `data-state=playing|paused|loading|error` on the player root; drive the glyph from CSS. Keep BOTH glyphs in the DOM per SPEC-craft §8 and cross-fade with its exact values (`scale 0.25→1`, `opacity 0→1`, `blur 4px→0`, `cubic-bezier(0.2,0,0,1)`) — never toggle `display`. Update `aria-label` to "Pause"/"Play". The mockup already ships the pause path at `canon/references/mockups/B-vault-balanced.html:128`. On `cr8:trackchange`, set `aria-current="true"` on the matching `.play-row` plus an inset era thread (`box-shadow:inset 3px 0 0 var(--era)`, never `border-left`) and a mono `playing` flag in the row's state cell. Add one polite `aria-live` region announcing title + version. Nudge the play triangle 2px right per SPEC-craft §4. While here, replace the blanket `prefers-reduced-motion` kill at `owner.css:404` with SPEC-craft §14's gentler rule.
**Accept:** Play a track: the glyph is a pause bar, `aria-label` is "Pause", and exactly one row carries `aria-current="true"` with the era thread. Pause: it inverts. Kill the network mid-track: the player shows an error state rather than silent confident chrome. Template test asserts both glyphs are present in `base.html` and that neither uses `display:none`. `grep -n 'transition:none!important' cr8/web/common/static/owner.css` returns nothing.

## 2. Nothing that writes may stop the music
**Why:** Applying a batch tag or committing metadata destroys playback. `owner.js:13` intercepts `form[data-cr8-form]` and either calls `window.location.assign(response.url)` (:23) or `document.open(); document.write(html)` (:28); `/batch` and `/songs/{ulid}/edit` both return `RedirectResponse`, so both take a full-navigation path that destroys the `hx-preserve`d `#cr8-player` and its `<audio>`. The queue survives in sessionStorage; the audio restarts at 0:00. The bulk-tagging workflow the owner needs most is the one that reliably kills the music.
**How:** Convert `/batch` and `/songs/{ulid}/edit` in `cr8/web/owner/routes.py` to `hx-post` returning fragments — affected rows out-of-band plus a toast — so `#cr8-main` is never fully replaced. Delete the `document.write` branch; the auth pages that needed it have no player, so a normal form post is fine. Separately: `hx-preserve` on `#cr8-player` (`base.html:37-38`) is load-bearing, not redundant — htmx 2's default history element is `document.body`, so the Back button would otherwise replace the body and destroy the live `<audio>`. Set `htmx.config.historyCacheSize = 0` to stop writing ~2.8 MB of row HTML into localStorage on every navigation.
**Accept:** Start audio, select 12 rows, apply a tag, then hit the browser Back button twice and click three filters: `audio.currentTime` advances monotonically throughout and `audio.paused === false` the whole time. Add a regression test that submits the batch form and asserts the response is a fragment (not a 303) and contains no `<html` root. `grep -rn 'document.write' cr8/web/common/static/` returns nothing.

## 3. Canonical tag write path: song-scoped, and a chip can be un-pressed
**Why:** Two defects make tagging self-defeating. (a) `owner.js:226` only POSTs when `aria-pressed !== "true"` — clicking an applied chip skips the write entirely, so **no tag can be removed from any surface in the app**, on any screen. The server already toggles correctly (`reactions.toggle()` soft-deletes on repeat); the client throws the capability away. And `/batch` inserts into `song_tags` with `ON CONFLICT DO NOTHING` while no `DELETE FROM song_tags` exists anywhere in the web layer — a tag applied to 40 songs can only be undone by CSV round-trip. (b) Two stores hold the same concept: chips write `reactions(bounce_ulid, actor)`, batch writes `song_tags(song_id)`; reads union them in four places and discard `source` and `actor`. 96 songs have multiple bounces, so tagging v3 and opening v1 shows an unpressed chip on a song the filter already returns. Nobody tags fast when a mistake is forever and the state display lies.
**How:** Make `song_tags` the single canonical store for owner intent, keyed by `song_id`. Add `POST /songs/{song_ulid}/tags/toggle` (dim, value) that inserts or deletes and returns the rendered chip with true state; POST unconditionally from the client and render what comes back. Restrict deletes to `source='human'` so filename-derived collab tags are protected. Keep `reactions` for what it is good at — append-only, attributed, guest-origin opinion — and append an audit row there for the activity feed. Resolve pressed state by `song_id` using the bounce→song join `reactions._song_id` already performs; keep `bounce_ulid` on the row as provenance only. Carry `source` and `actor` through the union sites in `cr8/web/common/queries.py` (:436 and the three others) — A1's "derived tags render visually distinct" is unimplementable until they survive. In the same migration, widen the `song_tags.dim` CHECK from `('vibe','instr','collab')` to also allow `('use','problem')` — cheap against 33 rows, expensive after the first thousand tags — without shipping UI for them yet. Per SPEC-craft §6a the chip toggle must NOT animate: instant colour/fill change, sub-100ms opacity settle at most.
**Accept:** Toggle a chip twice through the HTTP layer: pressed → unpressed, and the row disappears from `song_tags`. Tag from bounce v3, open v1: the chip renders pressed. A pytest asserts the same song filtered by that value returns it after the first toggle and not after the second. `grep -rn "kind='chip'" cr8/web/owner/` shows writes only on the audit path. Migration applies cleanly and `PRAGMA integrity_check` passes.

## 4. The right panel becomes a real tag editor, bound to the cursor
**Why:** This is the literal answer to "how do I even tag stuff?" — from the desktop layout, you can't. `library.html:185` renders the section labelled "tag panel" as `<a class="chip" href="{{ item.url }}">` — navigation links, not toggles — and its `aria-pressed` means "this filter is applied", not "this song carries this tag", so the control actively lies. It renders `vibe` only (instr/collab/status/key absent despite §4), and with an empty vocabulary it prints "No vibe values yet." forever with no way to create a first value. Worse, `library.html:5` pins the whole panel to `{% set preview = songs[0] %}` while JS patches only six `data-detail-*` spec cells, so clicking row 30 shows row 30's key and BPM beside **row 1's** version rail, tags and cover. A partially-correct detail panel is worse than none: you will tag the wrong song.
**How:** Add `GET /fragments/detail/{song_ulid}` returning the entire panel — cover, spec grid, version rail, tag groups, stems — and hang it on the row with `hx-get hx-target="#detail-panel" hx-trigger="click, focus"` at ~120ms debounce, plus the same swap on `j/k`. Keep the `data-detail-*` attributes purely as an optimistic first paint so the panel never flashes empty. Rebuild the tag section as one chip group per dimension (vibe / instr / collab / status / keeper / key) where every chip is a `<button hx-post>` from item 3 with optimistic fill and commit-ack, plus an always-present "+ value" input with typeahead over `filter_vocabulary` showing each candidate's global count inline ("dreamy · 7 songs") so you reuse rather than invent. Render status/key/keeper (columns) and vibe/instr/collab (`song_tags`) through one shared Jinja chip macro parameterised by POST target — indistinguishable to the user, obviously different in the code. Delete `DEFAULT_CHIPS` at `queries.py:706` (SPEC-dig §4 forbids a hardcoded vocabulary); demote it to a dismissible "suggested" group shown only while the owner has fewer than eight values of their own. Replace `library.html:8`'s subtitle "Metadata first. Tags stay optional." — the app's own primary screen currently tells the owner that tagging is optional.
**Accept:** Click row 30: the panel's rendered `song_ulid` equals row 30's, including the version rail and cover. Tag it from the panel: audio does not stop, the URL does not change, the list does not re-swap, and the left-rail count increments. Type a brand-new value into the input on a catalog with zero vibe tags: it is created, applied, and appears as a rail facet. Template test asserts the detail tag section contains at least one element with `hx-post` — that single assertion stops this regressing to links. `grep -n DEFAULT_CHIPS cr8/web/common/queries.py` returns nothing.

## 5. Row cursor model: click inspects, Enter plays, four states never collide
**Why:** `library_rows.html` wraps everything except the checkbox and the 44px chevron in one `<button class="song-row play-row">`, so there is no way to look at a song, focus it, or tag it without hijacking the audio. Hover offers only a 3.5% background tint — an ~8/255 delta per channel, invisible on a desktop monitor in a lit room — and there is no selected state, no focus state, and nothing to distinguish the four states that co-occur constantly on a 472-row list (playing / cursor / selected / panel subject). SPEC-v2 §4 makes `j/k` the primary way to move through the library and `1–9` the way to tag the focused row, so focus visibility is the core interaction, not an accessibility checkbox.
**How:** Single click moves the cursor and swaps the detail panel (item 4). `Enter` or double-click plays. Add a hover/focus play glyph replacing the cover swatch, and a hover row-tail with heart, tag, add-to-queue and an overflow menu (play next, add to collection, rip stems). Keep the row a real interactive element per the no-bare-divs rule, but as a row widget whose activation is distinct from selection. Layer the four states so all four can render at once — never two on the same property: hover `background:rgba(255,255,255,.05)`; selected `.09` (hover-while-selected `.13`); playing `box-shadow:inset 3px 0 0 var(--era)` plus `font-weight:650`; focus a two-tone ring that survives a white chip fill and an `overflow:hidden` ancestor — `outline:2px solid #0a0a0a; outline-offset:-2px; box-shadow:0 0 0 2px rgba(255,255,255,.92)`. Add `.song-row{scroll-margin-block:88px 96px}` so `j/k` never parks the cursor under the sticky header or the player. Roving tabindex: the row is the only tab stop, in-row controls get `tabindex="-1"` (472 rows × 4 controls is ~1900 tab stops otherwise — the same failure as the 472 Remove buttons in QA §3). Rows are fixed 44px single-line with `content-visibility:auto; contain-intrinsic-size:0 44px`; tags truncate to `+N`. Do not server-render the per-row `<details class="row-versions">` at ≥1100px — the panel owns that job and it breaks the fixed-height contract. Scope `button:active{transform:scale(.97)}` away from rows.
**Accept:** Click a row while a different song plays: the panel updates, audio is untouched. Press Enter: it plays. A row that is simultaneously hovered, selected, focused and playing shows all four treatments legibly in a screenshot. Tab from the search field lands on one row, not on a checkbox. `document.querySelectorAll('.song-row [tabindex="0"]').length === 0`.

## 6. The queue is the whole result set, and shuffle tells the truth
**Why:** Three of the most-pressed controls in the app do something other than what they say. (a) `owner.js:39` builds the queue from `document.querySelectorAll('.library .play-row[data-track-url]')` — only the rows currently in the DOM — so clicking a row with infinite scroll at page 1 queues **60 songs, not 472**, and "shuffle everything" silently truncates at the pagination boundary. (b) `Queue.setShuffle(false)` flips a boolean but leaves `playQueue` in shuffled order, so shuffle-off changes nothing audible. (c) `Queue.reshuffle()` hard-sets `mode = "queue"`, so reshuffling while digging permanently disables `refillDig()` with no indication, and turning shuffle on restarts the song you were enjoying. `mode` exists in state and is never shown anywhere.
**How:** Always build the queue from `/api/library-queue` with the current filter query, never from the DOM — the endpoint already exists and is called on other paths (`owner.js:212`). Preserve `sourceQueue` order and rebuild `playQueue` from it when shuffle is turned off, splicing the current track into its natural position and keeping the cursor there; never restart audio on a mode toggle. Make `reshuffle()` mode-preserving. Surface mode and position in the player bar: "digging · 14 played" / "shuffling 34 dreamy" / "queue 12 of 60". Add a cover thumb, era chip and title that reveals the row in the list (scroll + cursor + flash), bound to `L` — after SHUFFLE EVERYTHING the queue is 472 shuffled tracks while the list stays sorted, and the two are currently unrelated with no way to find what you are hearing.
**Accept:** Load the library, click row 3 without scrolling: `Queue.length === 472`. Toggle shuffle off mid-track: audio does not restart and `next` plays the natural successor. Enter DIG, press reshuffle, let a track end: it still refills from DIG. The player bar reads "12 of 472" and the mode label matches the gesture used. Press `L`: the list scrolls to the playing row and flashes it.

## 7. The three entry gestures get a home, and DIG routes you at the untagged
**Why:** SPEC-dig calls shuffle/DIG "the core interaction" and "the three entry gestures (prominent)". SPEC-v2-desktop mentions `DIG` **zero** times and `shuffle` once, inside the Collections section — the §1 diagram has a nav bar, a rail, a list, a panel and a transport, and no home for any of them. They currently live in `.page-head`, which the new layout deletes; implementers will drop them or wedge them somewhere arbitrary. Separately, `prioritized_dig` (`queries.py:209`) weights only by play count and last-played, so the app's flagship serendipity gesture contributes nothing to closing a 472-song, zero-tag gap — and with only 26 playback events total the weighting is near-uniform anyway.
**How:** Place SHUFFLE EVERYTHING and DIG as a persistent pair at the right end of the 56px top bar (they are global). Put SHUFFLE THIS in the list's sticky header showing the live count — "shuffle these 34" — because it is defined by the filters immediately to its left. Add untagged-ness as the leading DIG signal ahead of play recency: never-played AND untagged first, then untagged, then never-played, then least-recently-played. Digging then *is* tagging progress with no dashboard and no guilt bar. Show the reason on the now-playing chip per A3 ("never surfaced", "not played since Mar", "no vibe yet"). Let DIG accept the current filter as its universe so "dig the dreamy ones I haven't heard" is one gesture, and add a DIG THE UNTAGGED action beside SHUFFLE EVERYTHING.
**Accept:** At 1440×900 all three gestures are visible without scrolling, and SHUFFLE THIS's label matches the count in the list header exactly as filters change. With zero tags in the catalog, ten consecutive DIGs return ten distinct untagged songs. Tag one, DIG twenty more times: the tagged song does not reappear before the untagged pile is exhausted. The now-playing chip states a reason.

## 8. Filter rail: the counts already exist — render them, and hide the dead groups
**Why:** The rail is the 472-row index and it is currently a blank column with no numbers. `queries.py:436` already computes `COUNT(DISTINCT song_id) AS frequency` for every value and the template throws it away, despite §1 explicitly asking for counts. Every facet renders as `.filters{overflow-x:auto}` with `scrollbar-width:none`, so most of the 24 Camelot values are invisible and unreachable with a mouse. `status` renders exactly one option ('demo', 472/472) — a dead control taking rail space. There is no combined readout of what is filtered, no clear-all, and each click is a full boost navigation that resets scroll and discards every infinite-scroll page you loaded.
**How:** Render the counts that are already computed. Convert facets to vertical collapsible groups in the rail, each scrolling internally with a real scrollbar (`scrollbar-gutter:stable`, `overscroll-behavior:contain`) and a type-to-filter box once a group exceeds ~12 values. Suppress any dimension with ≤1 distinct value. Add an explicit `— untagged —` pseudo-value at the bottom of every dimension with its own count — §4's untagged pile, currently 472/472 for vibe, and the single most important row in the rail right now. Add jump-to-era with live counts (NOVA1 254 · PELICANA 75 · working 68 · undated 75). Put an active-filter token strip with individual × and a clear-all at the top of the list region, beside the result count and SHUFFLE THIS. Ctrl/Cmd+click multi-selects within a dimension (OR); dimensions combine with AND. Every facet click is an htmx swap targeting the list + rail counts only, never a full-page navigation, and preserves scroll offset.
**Accept:** Every rail value shows a tabular count that sums correctly against the list. The status group does not render. Clicking two vibe values returns the union; adding an era narrows it. Applying a filter with 4 pages loaded does not reset scroll to top and does not clear a checkbox selection. Clear-all restores 472.

## 9. Backfill derived tags and give "undated" its own bucket
**Why:** Everything above lands on an empty vocabulary without this. `song_tags` holds 33 rows, all `dim='collab'`, all `source='filename'`; vibe and instr are zero; the `eras` table has **0 rows**. A rail whose primary content does not exist reads as broken, not empty, and SPEC-dig's payoff ("tag five things dreamy and shuffle dreamy is immediately worth having") pays out only after the owner has done the hard part unrewarded. Meanwhile `text.py:32` returns `("working","working")` for any null or unparseable date, so **75 undated songs (16% of the archive) render in `oklch(0.86 0.16 115)` — the brightest, most saturated token in the palette.** "We have no date" is currently the loudest signal on screen, and the 'working' group is 30% of the library, half of it fake. A1 already requires this layer; it is unbuilt.
**How:** Change `era_for_date(None)` to return `("undated","unknown")`, add `--era-unknown: rgba(255,255,255,.14)` as a neutral field (not a hue), render undated as its own sticky group and its own rail count. Populate the `eras` table with real ranges and write `songs.era_id`. Then materialize what the catalog already knows into `song_tags` with honest `source` values before manual tagging ships: `derived-key` / `derived-bpm` / `derived-era` / `filename` / `mixrole` — bpm covers 466/472, key and camelot 351/472, mixrole tokens (vox/novox/inst/bass/gtar/acap) sit unused in `bounces.mixrole`, and collab is already parsed for 33. Add bpm bands, duration bands, version-count>1 (96 songs) and has-stems as rail facets. Render derived chips at reduced opacity with a dotted underline; clicking one promotes it to `source='human'` or rejects it. Only vibe, use and keeper should ever require fresh human judgment.
**Accept:** On a clean checkout of the real catalog, the rail shows at least ten populated facets with non-zero counts before any human tag exists. No song renders in an era colour via a fallback path — `grep` the era resolver: the null branch returns the neutral. Derived chips are visually distinct from human chips in a screenshot, and one click promotes a derived chip to human with `source` updated in the DB.

## 10. Undo every tag write, with a toast — before any keyboard or bulk verb ships
**Why:** SPEC-v2 proposes single-keystroke `1–9` tagging on the focused row and contains the word "undo" zero times. That is a keyboard model that manufactures mistakes with no way to take them back. A `/reactions/{id}/undo` route exists but is reachable only from triage; chip toggles, hearts, `/batch` writes across an arbitrary selection, and `/songs/{ulid}/edit` have no undo path and no confirmation. During fast digging, mistags are guaranteed. This is a precondition for items 11 and 12, not a nice-to-have.
**How:** One session undo stack covering every tag write — chip toggle, heart, bulk add/remove, keeper — bound to `Cmd/Ctrl-Z` and `u`, backed by the append-only reaction model that already supports revert plus the new `song_tags` delete from item 3. A bulk write is one undo entry, not forty. Every write emits a toast in the player bar's status slot: "tagged 12 songs dreamy — undo", auto-dismissing at 30s. Per SPEC-craft §10 the toast may animate; the underlying chip state change may not.
**Accept:** Tag 12 songs from a multi-select, press Cmd-Z once: all 12 revert, rail counts return to their prior values, and audio never stops. Toggle a chip, untoggle it, press Cmd-Z twice: state walks back through both. Undoing a bulk write is a single keystroke, verified by a pytest against the HTTP layer.
